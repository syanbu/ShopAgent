# 多商品对比决策

> 状态：已完成
>
> 代码入口：`src/shop_agent/models/comparison.py`、
> `src/shop_agent/services/dashscope_chat.py`、
> `src/shop_agent/workflow/nodes.py`、`src/shop_agent/workflow/graph.py`

## 功能目标

在现有多轮商品推荐之后，支持用户从最近一轮展示的最多三款商品中选择两到三款，
围绕一个明确维度进行对比，并根据商品 JSON 中的真实资料给出有边界的选择建议。

典型对话：

```text
用户：推荐几款面霜
Agent：展示 A、B、C 三款商品
用户：A 和 B 哪个更保湿？
Agent：对比 A、B 的保湿证据，说明差异并给出推荐；证据不足时不强行判断。
```

本功能解决的是已知小候选集中的购买决策，不是从全量商品中重新召回候选，也不是基于
用户行为预测点击或购买概率的个性化推荐系统。

## 功能应用场景

该能力适合“用户已经看过少量候选，现在需要做选择”的多轮购物阶段。它依赖最近一轮
展示的两到三款商品以及一个明确的比较维度，不适合替代首次搜索或全库商品排行。

### 美妆个护：功效和肤感

```text
用户：推荐几款面霜
Agent：展示 A、B、C
用户：A 和 B 哪个更保湿？
```

系统从两款商品的结构化信息、官方问答、详情和评论中查找保湿相关证据。官方资料能支持
明确差异时给出胜出结论；只有零散评论或不同肤质反馈相反时，返回场景相关或证据不足，
不会虚构“保湿指数”。

### 数码产品：续航、拍照和规格

```text
用户：推荐三款手机
Agent：展示 A、B、C
用户：这三个哪个续航更好？
```

系统统一比较三款商品中已有的电池、充电、官方问答和体验资料。若不同 SKU 的容量或配置
不同，结论会明确限定到具体 SKU，必要时返回 `context_dependent`。

### 耳机与穿戴设备：降噪和佩戴体验

```text
用户：前两个对比一下降噪
```

官方参数或问答用于判断是否支持主动降噪、降噪模式等事实，评论只用于补充个人体验。
如果一款只有“感觉比较安静”的评论而没有可核实规格，系统会说明证据强弱差异。

### 服饰运动：重量、支撑和适用场景

```text
用户：第一款和第三款哪个更适合长距离跑？
```

当商品资料同时包含重量、缓震、支撑或适用场景时，系统可以做条件化建议；资料没有覆盖
“长距离跑”时，会返回证据不足，而不是借助模型常识替商品背书。

### 缺少比较维度时的澄清

```text
用户：A 和 B 哪个好？
Agent：你更想比较哪方面，例如价格、规格还是使用体验？
用户：保湿
```

系统把未完成的目标选择保存在 SQLite 会话状态中，用户补充维度后恢复原对比，不需要
重新说明 A 和 B。目标引用有歧义时也使用相同的可恢复澄清机制。

### 不适用场景

- 用户还没有获得最近候选：应先执行普通商品推荐。
- 用户要比较最近结果之外的任意商品：当前版本不重新搜索，需先把商品纳入最近候选。
- 用户问“综合最好”但没有评价维度：先澄清，不生成隐含权重。
- 用户希望基于销量、点击或个人历史做个性化排序：需要行为数据和独立推荐系统，不属于
  当前参赛 Demo。

## 范围

本功能包含：

- 新增独立的多商品对比意图和 Agent 工作流分支。
- 对比对象严格限定为 SQLite 会话中 `recent_candidates` 保存的最近一轮商品。
- 支持选择最近候选中的两款或全部三款，包括序数、位置、标题和品牌等自然语言引用。
- 从内存 `ProductCatalog` 按可信 `product_id` 读取完整商品 JSON。
- 使用商品标题、结构化字段、SKU、商品详情、官方问答和用户评论生成对比材料。
- 一次模型调用在统一上下文中完成所有目标商品的证据分析和对比结论。
- 对模型返回的目标商品 ID 和证据引用进行确定性校验。
- 支持明确胜出、平局、依赖使用场景和证据不足四类结论。
- 唯一胜出商品可成为会话焦点，供后续单商品追问使用。

本功能不包含：

- 引用最近一轮之前展示的商品。
- 根据任意商品名称重新执行全库搜索。
- 在目标商品已经确定后重新执行向量召回或语义重排。
- 协同过滤、双塔召回、Learning to Rank、用户画像或行为预测。
- AHP、TOPSIS、Copeland 等额外评分或排名聚合算法。
- 生成数据集中不存在的“保湿度”“修护指数”等数值分数。
- 把用户评论当作官方规格、成分或功效证明。
- 商品对比历史、完整商品 JSON 或模型对比结果的额外持久化。
- 新增客户端专用的结构化对比卡片或 SSE 事件；第一版沿用流式文本回复。

本功能复用 [多轮 Query 编译、稳定条件细化与指代消解](multi-turn-query-engine.md) 的
会话、候选域、指代校验、焦点商品和澄清机制。商品 JSON 继续是唯一权威事实源，
Qdrant 不参与已经确定目标商品的对比取数。

## 外部行为

### 目标选择

对比请求只允许从 `recent_candidates` 中选择商品。模型负责判断当前用户原文与每个最近
候选之间的语言关系，代码负责校验候选矩阵并生成可信的目标商品集合。模型不能直接
生成或选择可信 `product_id`。

第一版需要覆盖：

- “第一款和第二款哪个更保湿”
- “前两个对比一下”
- “第一款和第三款”
- “这三个哪个续航最好”
- “小米和三星这两款拍照哪个好”
- 使用客户端已经展示的 A、B、C 标签选择商品

目标不足两款、品牌引用命中多款但无法确定选择范围，或引用超出最近候选域时，进入
现有可恢复澄清流程，不执行商品取数和回答模型调用。

### 比较维度

用户明确提出“保湿”“续航”“重量”“价格”等维度时，系统只围绕该维度比较。若用户
只说“哪个好”且当前消息没有明确维度，第一版追问：

```text
你更想比较哪方面，例如价格、规格还是使用体验？
```

系统不根据常识自动选择评价维度，也不把当前目录中缺少证据的维度替换成其他维度。

### 商品材料

目标商品确定后，系统从 `ProductCatalog` 直接读取对应原始商品，构造带稳定来源标识的
对比材料：

1. 结构化商品字段与 SKU。
2. 官方问答。
3. 商品详情描述。
4. 用户评论。

事实冲突时沿用现有优先级。用户评论只代表个人体验；多条评论互相冲突时，回答需要
说明存在个体差异，不能用简单多数票覆盖官方资料。

商品材料来自本地 JSON，不执行 Embedding、Qdrant 搜索或 Rerank。实现时可以复用现有
Chunk 构造规则生成稳定证据 ID，以便模型输出和代码校验，但不得把派生 Chunk 视为新的
事实源。

### 对比结论

模型在一次调用中同时接收比较问题和全部目标商品材料，输出结构化判断和面向用户的
自然语言回复。后端完成结构校验和证据白名单校验后，才通过现有 SSE 协议发送回复。
允许的结论为：

| 结论 | 含义 |
|---|---|
| `winner` | 现有资料对某一商品形成明确的相对优势证据 |
| `tie` | 目标商品在当前维度没有可支持的明确高下 |
| `context_dependent` | 优势取决于肤质、季节、具体 SKU 或其他资料中明确存在的场景 |
| `insufficient_evidence` | 至少一个目标商品缺少完成比较所需的关键资料 |

只有 `winner` 可以携带唯一 `winner_product_id`。其他结论不得为了生成推荐而指定
胜出商品。模型不得把文本相似度、Rerank 分数或商品描述篇幅解释为属性强弱。

回答需要包含：

- 每款商品与比较维度直接相关的证据摘要。
- 能够由现有资料支持的主要差异。
- 明确结论及其适用条件。
- 资料不足、评论冲突或 SKU 差异等限制。

例如比较面霜保湿能力时，若一款商品只有用户评论提到“比较润”，另一款有官方问答明确
说明锁水和适用肤质，系统可以说明后者证据更充分，但不能据此生成未经提供的功效数值
或宣称适合所有肤质。

### 可判定唯一胜出的事实门槛

`winner` 需要目标商品之间存在可以直接横向比较的高可信事实，而不只是各自的宣传词。
可比较事实至少应满足：

- 指标定义一致，例如都使用“8小时后角质层含水量相对使用前的提升比例”。
- 测试条件一致，包括受试人群、环境、使用部位、用量、仪器和测试时间点。
- 结果绑定到明确商品与 SKU，不能把滋润型的结果扩展到同商品的所有型号。
- 来源等级可比，优先使用结构化规格或官方资料，不用评论数量决定功效胜负。
- 结果存在唯一且方向明确的优势，同时没有更高优先级的冲突事实。

为便于参赛 Demo 手工验证，三款面霜的官方问答中加入了明确标注为“演示模拟数据、
非真实产品宣称”的统一横向测试 `DEMO-MOISTURE-001`：

| 商品与参测 SKU | 统一指标结果 |
|---|---|
| 玉兰油大红瓶 50g 滋润型 | 8小时角质层含水量较使用前提升18% |
| 薇诺娜特护霜 50g 标准装 | 8小时角质层含水量较使用前提升26% |
| 理肤泉特安修复霜 40ml 滋润型 | 8小时角质层含水量较使用前提升38% |

在用户比较这三款的“8小时保湿”或泛化的“保湿”时，现有事实可以支持理肤泉参测 SKU
成为 `winner`。回答仍需说明结论只适用于该模拟测试条件和具体 SKU，不能扩展为所有
肤质、季节或型号下都更好。

### 指标判断的当前实现与业界量化方式

当前版本没有为“保湿”“续航”“拍照”等维度建立独立的评分公式。意图模型从用户原文
提取比较维度并确定最近候选，对比节点随后读取每款商品的标题、品牌、基础价格、SKU、
商品详情、官方问答和评论。`DashScopeComparisonAssessor` 在一次调用中接收全部目标
商品的材料，根据指定维度返回 `winner`、`tie`、`context_dependent` 或
`insufficient_evidence`。

价格、电池容量、重量等已经结构化的数值，目前也作为商品证据交给对比模型统一判断，
没有进入按维度编写的确定性计算器。后端不重新计算属性分数，主要负责校验目标商品集合、
证据 ID 归属、商品顺序和胜出结论。模型只能引用商品材料中的事实，不能根据常识补数值，
也不能自行生成“保湿度 85 分”之类的数据。

当前实现对不同指标采用同一套事实边界：

| 指标类型 | 当前处理 |
|---|---|
| 价格、重量、容量等直接数值 | 模型对照结构化字段；数值缺失时不能推断 |
| 电池容量等效果代理指标 | 可以判断容量大小，不能只凭容量宣称实际续航更长 |
| 续航、保湿等效果指标 | 优先寻找同口径横向测试；没有统一测试时根据官方资料和评论返回场景相关或证据不足 |
| 舒适、好看、肤感等主观指标 | 说明评论中的个体差异，不生成统一客观分数 |

比如“哪个续航更长”，5000mAh 只能证明电池容量，不等于真实续航。屏幕、芯片、系统
调度和使用负载都会影响结果。只有两款商品提供相同条件下的网页浏览、视频、游戏或综合
使用时长时，资料才支持直接比较续航。“哪个更保湿”也一样，成分和“滋润型”描述只能
作为间接证据；统一时间点的角质层含水量变化、经皮水分流失等测试结果才适合量化比较。

业界通常把属性效果分和推荐排序分分开。属性效果分回答“这款商品在某项能力上表现
怎样”，数据来自规格和统一测试；推荐排序分回答“当前用户更可能选择哪款”，还会加入
价格、库存、用户偏好、历史行为和业务约束。常见推荐系统采用候选生成、打分和重排三段
流程，但这种排序架构本身不能证明某款面霜更保湿或某款手机续航更长。

属性量化一般需要以下数据和规则：

- 为每个品类定义指标字典，记录指标名称、单位、方向、适用 SKU 和测试条件。
- 将不同单位和量级归一化到可比较区间，并使用固定行业基准或全品类分布，避免只对当前
  两三款商品做 Min-Max 归一化。
- 将综合指标拆成多个子指标。例如“电池体验”可以包含实际续航、充电速度和能效；
  “保湿”可以包含使用后不同时间点的含水量变化、保湿维持率和经皮水分流失。
- 由专家规则、用户选择或训练数据确定子指标权重。权重必须与问题一致，“续航更长”
  不应因为充电更快而改变胜负，“电池体验更好”才可以纳入充电指标。
- 将分数与置信度分开保存。置信度由来源等级、测试口径一致性、样本量、数据完整度和
  时效性决定；缺失值保持 `unknown`，不能按零分处理。

最简单的属性分可以表示为：

```text
attribute_score = Σ weight_i × normalize(metric_i)
```

这个公式成立的前提是每个 `metric_i` 都有统一定义和可比数据。分数还需要绑定商品、
SKU、测试协议和协议版本，不能把某个滋润型 SKU 的测试结果扩展到同商品的其他规格。
用户点击、成交和评论星级适合训练推荐排序，但会受到价格、曝光位置、促销和品牌影响，
不能直接作为功效真值。

如果后续扩展当前 Demo，优先增加常见结构化指标的确定性比较，再按品类建设指标字典。
获得同口径测试数据后，才引入归一化和加权评分；积累足够的点击、成交、退货和满意度
数据后，可以另外训练 Learning to Rank，用于个性化推荐排序，不替代属性事实判断。

参考口径：

- [Google 推荐系统概览](https://developers.google.com/machine-learning/recommendation/overview/types)：
  候选生成、打分和重排的三阶段结构。
- [Google 推荐系统 Scoring](https://developers.google.com/machine-learning/recommendation/dnn/scoring)：
  评分目标会直接影响最终排序，需要避免用错误目标优化推荐结果。
- [UL PCMark for Android Work 3.0](https://support.benchmarks.ul.com/support/solutions/articles/44002199331)：
  使用一致工作负载测试手机性能和电池续航。
- [DXOMARK Battery Protocol](https://www.dxomark.com/introducing-the-dxomark-battery-protocol/)：
  将手机电池表现拆分为续航、充电和效率。
- [CDC 皮肤水合与经皮水分流失测量研究](https://stacks.cdc.gov/view/cdc/248812/cdc_248812_DS1.pdf)：
  说明角质层含水量和经皮水分流失的测量口径及仪器差异。

### 会话状态

商品对比不修改 `query_snapshot`、`recent_candidates` 或 `seen_product_ids`。

- `winner`：保存唯一胜出商品为 `focused_product_id`，支持后续“它适合敏感肌吗”等
  单商品追问。
- `tie`、`context_dependent` 或 `insufficient_evidence`：清空旧焦点，避免后续裸指代
  错误落到比较前的商品。
- 对比解析或生成失败：不修改现有会话状态。

### 失败行为

- 商品 ID 不在最近候选域：按非法模型输出处理并纠正一次。
- 证据 ID 不属于对应目标商品：按非法模型输出处理并纠正一次。
- 目标商品已不在 Catalog：返回安全的商品资料不可用错误，不使用模型常识补全。
- 结构化输出纠正后仍非法：进入统一模型解析错误链路。
- 对比模型失败：发送现有安全错误事件，不生成无证据的兜底结论。

## 接口与数据

### 对外接口

第一版继续使用：

```text
POST /api/v1/chat/stream
```

请求体和 SSE 事件类型保持兼容。对比回复使用
`message_start -> text_delta* -> message_end`，不重复发送已经展示的商品卡片，也不新增
客户端必须解析的事件。

### 本轮意图

`TurnIntent` 增加 `product_comparison`。本轮结构需要表达：

```text
ProductComparison
  question: str
  dimension: str
  reference:
    surface_text: str
    candidate_matches[]:
      product_id
      selected
```

`candidate_matches` 必须按 `recent_candidates.rank` 顺序完整覆盖最近候选。模型输出的
`product_id` 只是对服务端候选的逐项复制，解析器先验证完整、有序、无重复且无域外 ID，
再由代码选择 `selected=true` 的两到三款商品。

若比较维度缺失，解析结果进入澄清，不调用对比模型。被暂停的对比请求需要保存目标选择，
用户补充维度后恢复原操作，不要求重新选择商品。

### 模型输出

对比模型使用受 Pydantic 校验的结构化输出：

```text
ComparisonAssessment
  dimension
  products[]:
    product_id
    evidence_ids[]
    supported_summary
    limitations[]
  outcome: winner | tie | context_dependent | insufficient_evidence
  winner_product_id: str | null
  reason
  response_text
```

代码必须确定性校验：

- `products` 与可信目标集合完全一致且顺序稳定。
- 所有 `evidence_ids` 属于对应目标商品的本次材料。
- `winner_product_id` 只在 `outcome=winner` 时存在并属于目标集合。
- `tie`、`context_dependent` 和 `insufficient_evidence` 不携带胜出商品。
- `winner` 中的每款商品至少引用一条本次材料中的证据；缺少横向证据时不能判定胜出。

模型提示要求 `response_text` 遵守和结构化结论相同的胜出结果与资料边界，不得加入未在
`products` 和 `reason` 中表达的新事实。当前版本不对自然语言回复再做一次语义模型校验，
避免增加第三次模型调用；确定性的商品、证据和胜出契约仍由代码执行。

结构化结果只存在于单次 LangGraph 状态，不写入 SQLite。SQLite 继续只保存现有会话状态，
不需要表结构迁移。

## 工作流

在现有 `resolve_reference` 和品类解析之后增加对比路由：

```text
parse_turn_query
  -> resolve_comparison_targets
       -> persist_clarification -> END
       -> load_comparison_materials
       -> assess_comparison
       -> persist_comparison_focus
       -> emit_comparison_response
       -> END
```

`load_comparison_materials` 对本地 Catalog 做确定性读取，不触发检索、聚合、重排和现有
单商品证据验证链路。`assess_comparison` 只负责基于白名单材料生成结构化判断；
`emit_comparison_response` 只发送已经校验的 `response_text`，不再调用模型或重新决定
胜负。第一版因此只有一次对比模型调用，不为三款商品拆分成多次成对判断。

## 关键决策

### 不引入复杂推荐算法

候选集合已经由最近一轮结果限定为最多三款，问题是基于商品资料进行购买决策，而不是
从海量商品中预测用户行为。协同过滤、双塔、Learning to Rank 等算法既缺少训练数据，
也不能直接证明“更保湿”或“续航更好”。

### 不使用 Copeland 或人为综合分

第一版使用一次模型调用统一比较全部目标商品，避免多次成对调用产生判断尺度漂移。
最多三款商品不需要额外排名聚合。没有统一量纲和标注数据时也不生成属性分数，避免
制造虚假精度。

### 对比评估使用独立低延迟模型

本轮意图解析继续使用 `CHAT_MODEL=qwen3.7-max`，保证多轮意图、候选指代、条件变更和
澄清恢复的解析稳定性。只有目标商品与比较维度确定后的证据评估使用独立配置
`COMPARISON_MODEL=qwen3.6-flash`，降低读取两到三款商品材料并生成结构化结论的等待
时间。对比模型仍执行相同的 Pydantic、商品 ID、证据 ID 和 winner 契约校验；切换模型
不放宽事实边界或安全失败行为。

`qwen3.7-flash` 不是当前阿里云百炼提供的文本模型 ID，因此默认使用官方 Flash 档的
`qwen3.6-flash`。部署环境可以通过 `COMPARISON_MODEL` 覆盖该值。

### 目标绑定与语义判断分离

模型理解“A 和 B”“前两个”等自然语言关系，代码将判断限制在最近候选域并生成可信目标
集合。模型不能通过生成商品 ID 扩大对比范围。

### 商品 JSON 是唯一事实源

SQLite 只提供最近候选 ID，完整商品内容从 `ProductCatalog` 读取。目标已确定时不再使用
Qdrant；这减少外部依赖和延迟，也避免把检索相似度误当作比较结论。

### 允许没有冠军

数据不完整是当前 Demo 的已知边界。`context_dependent` 和
`insufficient_evidence` 是正常业务结果，不是生成失败。能明确表达资料边界比强行推荐
更符合项目的防幻觉要求。

自动化验证覆盖：

- 最近两款和第一、第三款的明确选择。
- 三款全部比较。
- 序数、位置、标题、品牌和 A/B/C 标签引用。
- 目标不足、引用歧义、域外商品和缺少比较维度的可恢复澄清。
- 结构化字段、官方问答、详情和评论的证据优先级。
- SKU 不同导致 `context_dependent`。
- 商品资料不足时返回 `insufficient_evidence`，不强行生成胜出商品。
- 评论冲突时说明个体差异，不把评论升级为官方事实。
- 非法商品 ID、非法证据 ID 和不一致胜出结论的纠正与安全失败。
- 对比请求不调用 Embedding、Qdrant、Rerank 和普通候选选择。
- `winner` 保存焦点，非唯一结论清空焦点，失败不修改会话。
- SSE 保持现有接口兼容顺序。

实现使用 `ComparisonAssessment` 约束模型输出，通过工作流再次校验目标商品集合、证据
归属和胜出条件。单元测试覆盖成功、两类可恢复澄清、非胜出结论清空焦点以及非法证据
安全失败；集成测试覆盖先推荐再对比的 HTTP/SSE 完整路径，并断言对比阶段不触发普通
检索、聚合和重排。真实服务测试补充多目标引用解析，并在实际工作流中注入对比评估器。
